# Committed-snapshot rollback comparison

The candidate improved this overloaded loopback fixture's completed-work rate. It did not sustain the requested 16 DAG/s, so all ten negative load verdicts remain false. [Matched run 39752294239](https://github.com/STEVVVU/distributed-task-runtime/actions/runs/39752294239) compared frozen baseline `7ed42c3` with candidate `77f28f2` on one hosted runner using independent normal Go 1.27.3 binaries, identical production flags and separate build caches. Both real smokes and the candidate's worker-loss/coordinator-restart verification passed before measurement, alongside Go tests/vet/build and nine Python benchmark controls.

Every trial used two Go workers, a 4,096-integer shared root, an installed 20 ms Python parent and exact-sum child, 32 outstanding DAGs and 160 offers at 16/s for 10 seconds. Each completed DAG verified its output and task-attempt metadata. Fixture SHA256 was `2804d6361162e3f4d958ffa8ae7aeaea8a19fa3e255bd0396bba96b8dc5a08c6` in every trial. Five interleaved pairs reversed order on odd repeats. Throughput includes the full offer-and-drain interval. Latency begins at intended arrival and includes waiting; declines have no completion latency.

Median throughput was 7.82% higher and all observed throughput ranges were disjoint. Completion-count, latency and RSS ranges overlap, so those values do not establish improvements. Across 800 offers per arm, baseline finished 351 and declined 449; candidate finished 361 and declined 439. Every finished result was exact. Both arms had zero product failures, rejections or timeouts, and all processes/samplers exited without errors. These rates are an observed bounded-generator workload, not maximum service capacity. The driver still uses the original Python client scheduler; a future native k6 migration is separately planned.

The separate [baseline native profile](native-profile-plan.md#captured-overload-profile-and-candidate) attributed 2.02 of 8.96 sampled coordinator CPU seconds to serializing a rollback snapshot before every request. The candidate retains the bytes from the last successful bbolt transaction and reuses them only for rollback. It still serializes and durably writes every successful call before replying. Source review checked initialization, restart, lock ownership, request/reply aliasing and failure publication. The failed-commit regression also preserves an already accepted object and checks the reopened database. The retained snapshot has a memory cost; RSS sampling here does not isolate its allocation size. Worker Python-child CPU/RSS and the remaining end-to-end limiter are not fully attributed by this normal-build comparison.

The runner exposed four Linux cores, kernel 7.0.0-1017-azure/glibc 2.39 and Python 3.11.17. CPU model and total RAM were not recorded. `GOMAXPROCS=2`, `CGO_ENABLED=0` and `GOMEMLIMIT=512MiB` matched both sides. Profiles are excluded from these timing samples.
