# Full candidate benchmark campaign

The full candidate campaign failed its 16 DAG/s load target. It finished 71 of 160 offered DAGs and declined 89 because the generator had reached its concurrency limit. It recorded no task errors, rejections or timeouts. The other 50 of 51 trials passed.

The campaign used source `77f28f26a002f729496d7b2c5a02815132e5eeb3`, Go 1.27.3, Python 3.11.17 and four hosted Linux cores. The build set `CGO_ENABLED=0`, `GOMAXPROCS=2` and `GOMEMLIMIT=512MiB`. The coordinator and workers ran as separate processes on one host and communicated over loopback gRPC. The CPU model and total RAM were not recorded. This is not a six-node measurement.

Each measured DAG contains a `slow` parent and an exact-sum `total` child. The parent reads one shared root object. Completed-DAG throughput covers both task submissions, execution, result retrieval and the offer-and-drain interval. It is not a remote-task-dispatch rate. The harness's `dispatch_lag_ms` measures time from intended arrival until the Python load thread begins its action. It does not isolate coordinator-to-worker dispatch. End-to-end latency starts at intended arrival and ends after the exact DAG result returns.

The base 4,096-item input is 15,961 bytes with SHA-256 `2804d6361162e3f4d958ffa8ae7aeaea8a19fa3e255bd0396bba96b8dc5a08c6`. The frozen workload uses seed 421, 32 DAGs per axis trial and five repeats per cell.

## Offered-rate runs

At 1 DAG/s, the 10-second sweep completed all 10 offers. At 4 DAG/s, the 10-second sweep completed all 40. The selected 120-second run offered 4 DAG/s and completed all 480 exact results. Its end-to-end p50, p95 and p99 were 519.876, 809.847 and 997.806 ms. Its p99 Python scheduler-start lag was 29.975 ms.

The 16 DAG/s, 10-second sweep scheduled 160 offers. It completed 71 and recorded 89 generator declines. Its end-to-end p99 was 14,213.985 ms. Its p99 scheduler-start lag was 16.902 ms. The declines reflect the driver reaching its 32-request concurrency limit, not product error responses.

The harness uses scheduler-start lag below 100 ms and end-to-end p99 below 5 seconds to choose a rate for the stability run. These thresholds are engineering-screening criteria. They do not establish a production SLA, and scheduler-start lag is not remote dispatch latency.

## Fault runs and evidence limits

The worker-loss and coordinator-restart trials each completed one exact DAG with result 822. In both trials, the retried `slow` task finished on attempt 2, the `total` task finished on attempt 1, and each published object key matched its final attempt. All trial processes and samplers exited cleanly. These two fault trials are single observations, not reliability estimates.

The compact [receipt audit](2026-10-22-full.json) records the source and summary hashes, per-cell ranges, outcome counts and fault results. The raw hosted run is [GitHub Actions run 39753709129](https://github.com/STEVVVU/distributed-task-runtime/actions/runs/39753709129). No latency or RSS improvement follows from this campaign. The earlier matched comparison's 7.82% completed-work-rate gain remains confined to its own five-pair overloaded fixture, documented in [the rollback comparison](2026-10-22-rollback.md).

Run `python tools/benchmark.py benchmark` on isolated Linux to reproduce this workload. The run does not identify the remaining throughput limiter because it collected no profile for this workload. It does not model six separate nodes, and it does not support claims of 1,600 tasks/s or a 4.8x speedup. Raw timings include the full two-task DAG path and a single-host loopback environment.
