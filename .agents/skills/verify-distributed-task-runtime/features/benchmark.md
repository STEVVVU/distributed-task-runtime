# Frozen benchmark

`python tools/benchmark.py smoke` reuses the installed Python API and real Go binaries, performs a warm DAG and one measured-for-instrumentation DAG on two workers, checks the exact arithmetic result and retains confirmed owned cleanup. This is a correctness smoke, not a performance result. `python -m unittest discover -s tools -p test_benchmark.py -v` checks axis coverage and timeout accounting.

`python tools/benchmark.py benchmark` requires isolated Linux execution. Version 1 uses seed 421 and a nine-cell one-axis-at-a-time design around two workers, 4096 object items, 20ms task delay and concurrency eight. Axes cover workers 1/2/4, object items 16/4096/32768, delay 0/20/200ms and concurrency 1/8/32. Five repetitions reverse cell order on alternating repeats. Each cell owns fresh state and starts with an untimed warm DAG, followed by 32 DAGs through trusted `slow` and `total`. One-worker cells are a matched worker baseline; other axes compare their same-base neighbor. This avoids an unrequested Cartesian explosion while covering each frozen axis. Fixed-rate 1/4/16 DAG/s sweeps run for ten seconds, then the highest zero-loss rate with dispatch-p99 <100ms and end-to-end-p99 <5s runs for 120s. Queues beyond concurrency32 are explicit generator declines. Separate one-DAG worker-loss and coordinator-restart journeys observe assigned work before injection and require a higher accepted attempt plus the exact result.

Raw `.runs/benchmark-*/` receipts retain source/dirty state, environment, workload, input hashes, intended arrival/start/result timestamps, outcomes, exact task IDs and state, peer transfers and Linux /proc CPU/RSS for tracked processes and generator at 100ms. Client retries and 50ms result polling are included in latency. CPU ticks require the retained clock-tick conversion. Windows smoke resource fields are null. The generator CPU sample covers all threads; worker Python child CPU is currently not included in the tracked-process counters, so aggregate runtime CPU cannot be claimed from these counters alone.

`profile` retains generator cProfile and Go scheduler/GC traces separately. It does not provide a Go hot-path CPU profile. Capture that profile before any cause-dependent optimization; do not assert a service limiter from these traces alone. The manual read-only `Runtime benchmark` Ubuntu workflow builds the actual binary, runs self-check and real smoke, then retains selected receipts, never local tokens or database contents. No performance result is yet published.
